DATA FORMAT MAPPING
-------------------

Source: Nuclei_*.csv (CellProfiler output)
  Columns:
    ImageNumber           — always 1 for single-ROI files
    ObjectNumber          — cell ID (1-based)
    AreaShape_Area        — nucleus pixel area
    Intensity_MeanIntensity_{MARKER}  — 18 markers (0.0–1.0 normalized)
    Location_Center_X     — spatial X
    Location_Center_Y     — spatial Y
    Number_Object_Number  — duplicate of ObjectNumber

  Example: Nuclei_40442ROI01.csv has 23,925 cells x 22 columns.

Target: DAS triplet ({stem}_df.csv, {stem}_obs.csv, {stem}_dfxy.csv)
  df   — index=cell_id, columns=marker names, values=expression
  obs  — index=cell_id, columns=metadata + threshold labels
  dfxy — index=cell_id, columns=[x, y]

Mapping:
  df columns   = strip "Intensity_MeanIntensity_" prefix → ASMA, CD11B, ...
  dfxy         = Location_Center_X → x, Location_Center_Y → y
  obs          = ObjectNumber, AreaShape_Area, slide_scene (from filename)
                 + threshold columns added later (thresh_CD8 = "+" / "-")

This is a straightforward pandas reshape. ~30 lines of code.


EXPECTED OUTPUT: studythresholds.csv
------------------------------------
Format (from KBPSGL1_V1_studythresholds.csv):
  Row index  | Markers | Nuclei_40442ROI01 | Nuclei_42092ROI01 | ...
  1          | Area    | 22                | 22                | ...
  2          | ASMA    | 0.1021            | 0.1023            | ...
  3          | CD11B   | 0.1008            | 0.1017            | ...

  - Rows = markers (18 in this panel)
  - Columns = ROI identifiers (Nuclei_{slide}ROI{nn})
  - Values = the NUMERIC threshold (not +/- labels)
  - "Area" row holds a constant (nucleus area threshold? always 22-23)

Key difference from current mailbox format:
  Mailbox CSV:  column,index,label   →  per-cell +/- assignments
  studythresholds.csv:                →  one numeric value per marker per ROI

The mailbox doesn't store the numeric threshold — only the resulting labels.
The threshold editor DOES know the numeric value (user drags a line), but
saveThreshold() currently discards it and only sends per-cell labels.

Fix: saveThreshold() must also emit the numeric threshold value.
Either add it to the existing mailbox payload or maintain a parallel store.

########## CODEX ##########

I would not start a fully separate thresholding project yet. The clean split is one shared thresholding/viewer runtime with two entry paths:

1. DAS project path: existing df/obs/dfxy + mailbox behavior stays intact.
2. Lab-native standalone path: Nuclei_*.csv + label_*.tif + channel TIFFs are adapted into the same payload shape the current threshold runtime already consumes.

Phase 1 should be an IO adapter, not a runtime fork. The adapter should do a few explicit jobs and fail flatly when they do not work:

- discover one ROI or study folder
- identify the useful Nuclei_*.csv and label_*.tif
- identify expression columns and the object/label id column
- verify that CSV object ids overlap segmentation label values
- build cell rows with both a stable viewer id and the native integer label id
- reuse the existing image/segmentation overlay machinery where possible
- write a threshold-focused viewer run plus a studythresholds.csv export path

The main contract I would protect is: threshold values are always stored in raw expression units. Display transforms are visual only. That keeps mailbox output, studythresholds.csv output, and future threshold reloads from becoming ambiguous.

I would avoid a Python stateful threshold backend for Phase 1 unless it is just the existing mailbox helper in a new coat. Browser-local pending thresholds plus explicit CSV export is easier to reason about and less likely to create cross-OS path surprises. Direct write is a bonus when the helper is available; download/export must remain first-class.

The highest-risk Phase 1 pieces are not the UI. They are naming and identity:

- Which CSV file is the real cell table when counts/threshold files are nearby?
- Which column maps to segmentation labels?
- Are label ids unique only within ROI or across the study?
- Does the label TIFF use the same orientation/shape as the displayed channel TIFF?
- What exactly is the expected studythresholds.csv schema?

I would make the standalone path produce a small debug/report file every run listing the chosen CSV, segmentation TIFF, channel files, label column, marker columns, object count, mask-label overlap count, and output threshold file path. That is cheap and will prevent most mystery failures.

Phase 2 can add a dedicated thresholding page if the main viewer feels too crowded, but it should still consume the same payload. Good Phase 2 features are threshold reload, multi-threshold overlay toggles, per-marker colors, channel switching, and better scale transforms. For the scale question, I would stop guessing log bases soon and add transform modes like raw, log10(x+pseudocount), and asinh(x/cofactor), with raw-unit saves only.

ARCSINH TRANSFORM
------------------

Worth doing in Phase 1. The current log10(x+1) with 0-1 data is
nearly useless — it compresses the entire dynamic range into 0–0.301.
The threshold line is the core UX and its usability depends on the
scatter plot showing meaningful separation.

Arcsinh is ~5 lines of JS in the scatter plot renderer:
  - Add a transform dropdown: Raw / Log / Arcsinh
  - Transform display coordinates only, not saved threshold values
  - Default to Arcsinh for FCS-like data (0-1 range)
