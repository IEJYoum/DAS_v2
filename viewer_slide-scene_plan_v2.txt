viewer slide_scene identity plan v2
===================================

Phase 1: core = slide_scene everywhere
---------------------------------------

This is the high-value change. After Phase 1, the core_tiles dict keys,
tile["core"], roi_data keys, threshold_store roi_ids, and obs-derived
groupings all use the same slide_scene string. No new abstractions, no
manifest object, no resolver function. Just wire existing code to use
slide_scene as the core key instead of deriving A1/B2 labels.

Phase 2 rewires segmentation lookup. Phase 3 deletes dead code. Phase 4
handles the FCS adapter. Each phase produces a working viewer.

4d. Freeze FCS slide_scene format
-----------------------------------

Per discussion: the FCS adapter produces slide_scene strings like
"40393ROI01" (no underscore, zero-padded ROI number from the CSV filename).
This is whatever parse_object_csv_filename() extracts. Don't change the
format — just stop converting it to "A1" for core keys.

What NOT to change
===================

- build_templates(), collect_scene_keys(), build_core_buckets() internals:
  These functions discover and resolve file paths using filesystem patterns.
  They are adapter-level code. They still use (letter, number) tuples
  internally. The only change is how their output is keyed when passed to
  build_catalog().

- Template resolution: resolve_template_for_scene() still substitutes
  scene keys into path templates. This is filesystem adapter work.

- Viewer JS runtime: the JS treats "core" as an opaque string key. Changing
  its value from "A1" to "40393ROI01" doesn't break any lookup. The only
  visible change is sort order and display labels in the tile grid.

- display_label: slide_scene.replace("_", " ") or just slide_scene. Don't
  add formatting rules. The JS can display whatever string it receives.

- TMA layout: if core keys change from "A1"/"B3" to slide_scene strings,
  the JS grid parser may fall back to compact layout. That's fine for v1.

- Subset overlay generation pipeline.

- Channel asset rendering pipeline.

- localStorage threshold persistence.

- Overlay canvas architecture (previewLayer + savedOverlayLayer).

Open question for Codex
=========================

In step 1b, the re-keying of by_core from tuple keys to slide_scene keys:
should this happen inside build_core_buckets() (cleaner but touches more
template resolution code) or as a post-processing step in build_catalog()
(simpler, fewer lines touched)?

My recommendation: post-processing in build_catalog(). build_core_buckets()
continues to use tuples internally for template resolution. build_catalog()
re-keys the output before building tiles. This keeps the filesystem adapter
code (template resolution) untouched.

The mapping from tuple key to slide_scene comes from:
  1. obs["slide_scene"] if available (preferred — exact match)
  2. extract_slide_scene_from_path() on the first resolved TIFF (fallback)
  3. core_name_from_key() (ultimate fallback — preserves old behavior)

After Phase 3, fallback 2 and 3 are deleted. Only obs["slide_scene"] remains.
